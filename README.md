# 提交命令

git add . & git commit -m "update" & git push origin main

# 日常流程建议

所以，把你的日常动作固化成这套“三步闭环流”，你的 Git 这辈子都不会报错：

1. **坐下开工** ：先敲 `git pull origin main`（同步时空）。
2. **快乐码字** ：本地疯狂写论文、调模型、跑实验。
3. **写完收工** ：敲那串长命令 `git add . && git commit -m "update" && git push origin main`（发送成果）。

# 提交一次分三步的必要性

1. `git add`：挑选物品（挑选哪些变动要打包）

> 📦  **比方** ：你面前有一大堆杂物（你今天修改的所有文件），你现在拿出了一个快递盒，把想寄走的东西 **一件一件扔进盒子里** 。

为什么不能没有它？（必要性）

在日常工作中，你本地的文件夹里经常会产生很多“不需要上传”的垃圾和临时文件。

* 比如：你写完论文，编译出的临时缓存文件；或者你写代码时自动生成的日志、测试用的临时草稿。
* 如果没有 `add`，而是直接一键全部同步（像网盘那样），这些垃圾文件就会把你的云端仓库塞满。
* **`add` 的核心价值在于：精准筛选。** 我改了 10 个文件，但我觉得其中 3 个还没写好，那我就只 `git add` 那 7 个写好了的文件，剩下的留在本地继续改。

2. `git commit`：封箱、贴标签（建立一个历史存档点）

> 🏷️  **比方** ：你把东西装好后，用胶带把快递盒 **彻底封死** 。然后在纸箱外面用马克笔写上： *“这是第一章的论文初稿，里面包含 2 张图”* 。

为什么不能没有它？（必要性）

**这是 Git 最核心的一步，它是“时光机”的存盘点。**

* **如果没有 `commit` 只有 `push`** ：你的云端就像一个无底洞。你今天上午传了一次，下午传了一次。下周导师把你痛骂一顿，让你“改回上周四下午那个版本”。如果没有 `commit` 记录，你根本不知道哪次上传对应的是什么状态，你面对的只是一堆乱麻一样的文件。
* **`commit` 的核心价值在于：对当前状态做“快照”并写注释。** 每一个 `commit` 都是一个安全的“存档点”。哪怕你明天把论文改得一团糟，只要你想，随时可以一键让整个文件夹瞬间穿越回任何一个 `commit` 的状态。
* **而且，它是在本地完成的** ：断网的时候，你依然可以疯狂 `commit`，在本地记录你的几十个版本，等有网了再统一寄出去。

3. `git push`：快递车出发（同步到云端）

> 🚚  **比方** ：你把封好的、贴了标签的快递盒， **交给快递小哥，装车运往大本营（GitHub）** 。

为什么不能没有它？（必要性）

这步最容易理解，它负责 **网络传输** 。

* 即使你本地包裹封得再好（`commit` 了 100 次），只要不执行 `push`，网络上就没有任何人能看到你的改动。
* **`push` 的核心价值在于：多端共享和备份。** 它把你在本地电脑上做好的“一连串历史包裹”，原封不动地同步到 GitHub 服务器上。你的另一台电脑执行 `pull`，就是去大本营把这些包裹接过来，在本地拆开。

# 提交命令的每个参数是什么意思？

这一串命令其实是用 `&` 拼接起来的 **三个独立命令** ：

$$
\text{命令 1} \quad \& \quad \text{命令 2} \quad \& \quad \text{命令 3}
$$

#### 第一部分：`git add .`

* `git`：调用 Git 软件。
* `add`：把文件塞进“暂存区”（就像寄快递前，把东西放进快递盒）。
* `.`：代表 **当前目录下的所有文件和文件夹** 。

#### 第二部分：`git commit -m "update"`

* `commit`：正式封箱、盖章、并记录版本（把快递盒用胶带封死，写上寄件人）。
* `-m`：意思是 "message"（备注信息）。
* `"update"`：双引号里是你自己写的字，用来告诉未来的自己“这次我改了啥”。你可以写 `"修改了第一章"`。

#### 第三部分：`git push origin main`

* `push`：把本地封好的箱子 **推送到云端** 。
* `origin`：GitHub 云端仓库的默认代号（指代你在网页上的那个网址）。
* `main`：你的主分支名称（GitHub 默认的主线叫 `main` 或 `master`）。

# 命令历史是针对每一个文件夹都有一个吗？

**不是，它是针对你当前打开的“终端黑窗口”的。**

* **终端的历史记录** ：你在 CMD 或 Git Bash 里按“方向键上键（↑）”，调出的是 **你这台电脑最近输入过的命令历史** ，它不管你当前在哪个文件夹。你在 `D:\LLM` 输入过这句话，去到 `C:\` 按上键一样能调出来。
* **Git 的历史记录（Commit 历史）** ：这才是针对文件夹（仓库）的。当你进去 `my_paper_markdown` 执行 `git log` 时，看到的是这篇论文的修改历史；如果你进到另一个写代码的文件夹，看到的就是代码的历史。两者互不干扰。

# 可以指定只更新某一个文件吗？

**当然可以！这也是 Git 的强大之处。**

如果你今天既改了 `6_社交行为聚集性分析.md`，又改了 `README.md`，但你 **只想把第一篇论文传上去** ，你可以精准指定文件名，绕过其他文件。

把命令里的 `.`（代表全部）换成你的**具体文件名**即可：

**Bash**

```
# 1. 只把这一个文件塞进快递盒
git add 6_社交行为聚集性分析.md

# 2. 封箱并备注
git commit -m "仅更新社交行为这篇论文"

# 3. 推送
git push origin main
```

这样，你在本地改乱了的其他文件（比如还没写完的草稿）就不会被顺便传到 GitHub 上去了。

# GitHub 的容量有限制吗？

**有，但它的限制逻辑和百度网盘完全不同。**

百度网盘限制的是你的 **个人总容量** （比如非会员 50G）。而 GitHub  **完全免费且不限制你的个人总容量** ，你建 100 个仓库，每个仓库放点代码或笔记，它完全不管。

但是，GitHub 限制的是**单个仓库的大小**和 **单个文件的大小** ：

* **单个仓库总容量：** 建议不超过  **1G** ，超过 5G 会被 GitHub 官方发邮件警告并限制写入。
* **单个文件大小：** 超过 **50MB** 会报警提示，超过 **100MB** 会直接拦截， **绝对不让你上传** 。

> 💡  **核心避坑指南** ：你的 Markdown 笔记和图片（通常几百 KB 到几 MB）这辈子都不可能用超。但 **千万不要把大模型权重文件（如 `.safetensors`, `.bin`）、几百兆的压缩包、或者 4K 视频放进这个文件夹里** ，否则 `git push` 会直接报错崩掉。

# 不同设备修改之前先pull

**场景：经典的“多端开工”或“网页端留痕”（不先拉就会炸）**

假设今天下午你在学校机房，登录 GitHub 网页端临时修改了 `6_社交行为聚集性分析.md` 里的一个错别字。这时候， **云端产生了一个新版本（版本 B）** 。

晚上你回到宿舍，打开自己的笔记本。你笔记本里的文件状态还停留在 **昨天的老样子（版本 A）** 。你没敲 `git pull`，而是直接兴高采烈地开始写论文的第四章，写完之后提交了一个 **新版本（版本 C）** 。

这时候，时空开始错乱了：

**Plaintext**

```
               ┌──> 网页端修改：产生了 [版本 B] (云端现在停留在这里)
               │
基准 [版本 A] ─┤
               │
               └──> 笔记本修改：产生了 [版本 C] (你本地试图推这个上去)
```

当你在宿舍电脑里敲下 `git push` 的那一瞬间，GitHub 会啪的一下把你的请求弹回来，并抛出一个红色的报错：

> `[rejected] main -> main (fetch first)`
>
> `error: failed to push some refs to...`

 **Git 的潜台词是** ：“兄弟，云端现在已经走到 [版本 B] 了，而你的本地代码居然是基于老掉牙的 [版本 A] 改出来的。你如果强行推上去，就会把我网页上的 [版本 B] 给无情覆盖掉！我拒绝执行，你必须先把云端的最新变化给我拿下来！”

🛠️ 怎么优雅地解决这种时空冲突？

这就是为什么我们要养成“开工前先敲一句命令”的习惯。

当你坐在电脑前，准备开始写新一章论文或者改代码之前，先别急着动笔，顺手在 Git Bash 里敲一行：

```
git pull origin main
```

这句话的意思是：“去 GitHub 云端瞅一眼，把最新的历史记录拉下来，和我的本地电脑融为一体。”

会发生两种情况：

1. **如果你之前没在别的地方改过** ：终端会提示 `Already up to date`（已经是最新啦）。你没有任何损失，可以安心动笔。
2. **如果你在别的地方改过** ：Git 会自动把别处的改动合并到你眼前的文件夹里。你的电脑瞬间同步到了宇宙最新状态，接下来你再怎么改、怎么 push，都绝对不会再撞车。

# 不常用命令

#### git reflog

#### 回退

是的， **正常来说，回退到过去绝对不需要、也不应该做任何修改** 。

你可以把回退到过去（`git checkout [版本号]`）完全理解为“去历史档案馆查阅资料” **或者** “看恐怖电影时倒带”。

#### 正确的“回退”姿势：纯看、不动

当你通过 `checkout` 回到某个历史版本时，你唯一的目的通常只有两个：

1. **查阅/对比** ：“我记得两周前我写过一段关于‘聚集性指标’的统计学推导，后来被我删了。我得退回去把那段文字复制出来。”
2. **抓bug** ：“我的代码/模型今天跑不通了，我得退回到昨天下午那个能跑通的版本，看看当时我的参数是怎么配的。”

在这些场景下，你的动作都是“只读（Read-Only）”的。看完之后，把需要的旧资料复制一下，接着直接拍拍屁股敲 `git checkout main` 闪现回到今天。这才是最标准的工业级操作。

🛠️ 那如果我回退之后，发现旧版本“更好”，我就是想改怎么办？

如果你回到过去后，一拍大腿觉得：“完蛋，我这三天的论文全写歪了，我不要现在的最新版了， **我要从这个旧版本开始重新写** ！”

这时候，**依然不应该在原地直接改**。正确的操作是“把过去的版本借尸还魂，变成今天的新版本”。有以下两种做法：

**做法 A**：在过去分叉出一条“新支线”（最安全，推荐）

你退回过去后，直接就地建立一个新分支（Branch），相当于开启一个平行的文字宇宙：

**Bash**

```
# 1. 别在原地改，直接基于这个旧节点建立一个叫 new_ideas 的新分支
git checkout -b new_ideas
```

这时候你的 `HEAD` 就安全了，你可以在这条新支线上随便改、随便 `commit`，完全不会弄丢原本的 `main`。

**做法 B：**直接物理抹除未来（最暴力，需谨慎）

如果你铁了心要彻底倒退，把未来三天的痕迹从地表抹去，你在 `main` 分支上直接执行：

**Bash**

```
# 直接把当前的主线强行倒退到这个旧节点，未来的修改彻底不要了
git reset --hard 46749e7
```

这时候你连时空都不用穿越，你的“今天”直接就变成了“过去”，接下来你直接在原地继续写就行了。

🏁 总结

所以，你的直觉非常准：**回退到过去，在 Git 的设计里就是一个“查阅”行为。** 只要你进去了旧版本，管住自己的手，不敲保存、不敲 `commit`，看完就走，Git 的时光机用起来就会像翻书一样安全、丝滑。

#### 分支

你的直觉真的太准了，这个“树枝接到树干上”的比喻简直绝了！这其实已经抓住了 Git 核心设计里最精妙的部分。

针对你的两个关键点，我们可以用你这个完美的“树树理论”来彻底捋顺：

原来的 `main` 确实变成了“非最新版本”

**你的理解完全正确！**

合并前，老 `main` 是树干的“顶端”（最新状态）。合并后，树枝（分支）上的新果实被接了过来，树干往上长了一截。

这时候，原本那个老 `main` 所处的节点，就退位变成了树干的“中段”——也就是你说的 **非最新版本（历史版本）** 。它变成了过去的一个年轮，静静地躺在历史记录里，供你随时用时光机倒带回来查看。

2. 合并之后，分支就会消失吗？

**答案是：它不会自发消失，但它已经完成了历史使命。**

用你的树枝比喻来解释，合并（`merge`）更像是“把树枝上的成果（果实/叶子）复制或者挪到了树干的顶端”。

执行完合并命令后，那个叫 `test_model` 的“树枝” **其实依然挂在树上** ，Git 绝对不会擅自帮你把它砍掉。它的状态是：

* 树干（`main`）现在拥有了树枝上所有的最新成果。
* 树枝（`test_model`）也还指向同一个成果。

因为成果已经安全进入主干了，这个旧树枝留着就变成了“冗余结构”。所以按照标准的工业规范，合并完之后，大家都会顺手敲一行命令把这个树枝 **主动砍掉** ：

**Bash**

```
# 成果安全了，把本地的 test_model 树枝砍掉
git branch -d test_model
```

只有当你亲手执行了这句命令，分支才会真正消失。

🌲 终极画面：Git 到底是怎么“接树枝”的？

在实际开发中，Git 接树枝有两种完全不同的手法（对应两种合并方式），画面感极强：

手法 A：直接把树干“拔高”（Fast-forward 快进合并）

如果你的树枝（分支）在疯狂往前长的时候，树干（`main`） **在原地停滞不前，没有长出新分叉** 。

那么合并时，Git 根本不需要做任何缝合。它直接把树干的顶端“往上拔高”，让树干顶端直接变成树枝的顶端。这种情况下，连“树叉”的痕迹都不会留下。

手法 B：打一个“时空补丁”（Three-way merge 三方合并）

如果你的树枝在长的时候，你或你的同学在树干（`main`）上也 **同时在往前写新东西** （树干自己也长高了）。

这时候两边都有了不同的新成果。当你执行合并时，Git 会展现真正的技术：它会把树干的最新成果和树枝的最新成果强行揉在一起，在树干顶端凭空结出一个“聚合果实”（被称为 Merge Commit）。

这时候在你的历史树状图上，你会清晰地看到：树干分叉出去一根树枝，最后这根树枝又 **弯回来合进了树干** 。

所以，你说的“把树枝接到了树干上”不仅是一个比喻，它就是 Git 底层图形学（有向无环图 DAG）在现实世界里最完美的映射！
